# 协议 0002：ultracode v2.0 桌面实测与验收（D 系列 + U' 系列）

> 产出日期：2026-11-07。配套设计：`0001-ultracode-dwf引擎版设计方案.md` §7。
> 环境：ZCode.app 3.17.2，插件 2.0.0（全局安装或 marketplace 安装均可）。测试目录建议：`ultracode-lab`（git 仓库）。
> 每项记录：操作、观察、判定（PASS/FAIL/BLOCKED）。结果回写本文件与设计文档 §7。

## 前置准备

1. 重启 ZCode（或新会话）；确认手册已更新：新会话里技能描述应含「dwf 引擎版」。
2. `zcode skills list --json` 应看到 ultracode（user scope）。

## D 系列：源码结论的桌面校准（源码仓库新于 3.17.2，逐项验证）

| # | 项 | 操作 | 判定标准 |
|---|---|---|---|
| D-a | facade 签名/命名空间 | 新会话：`/ultracode 扫描 src 下所有 .ts 文件，每个文件派一个子代理概括职责`（无 src 则任选目录） | 模型能写出含 `agent().ask<T>` 的脚本并通过编译；骨架中 `files.glob`/`git.*` 命名空间形态与源码一致（若 3.17.2 命名不同，记录实际形态并回改手册 §5 头注） |
| D-b | saved workflow | 让模型把一个简单脚本存档：`把刚才的工作流存为 scan-dirs`，再 `按名运行 scan-dirs` | 存档落 `.zcode/workflows/`（项目档）；按名运行走 saved 通道且可传 args；记录 3.17.2 是否支持 |
| D-c | worktree 骨架（**硬需求**） | 在 git 仓库：`/ultracode 并行改 3 个文件，每文件一个子代理，按手册骨架 D 用 worktree 隔离` | 三个 worktree 创建成功、各自动 commit、run 结束后主代理逐一 diff 并征询合并、收尾清理无孤儿（`git worktree list` 为空） |
| D-e | 确认窗体验 | 观察 D-a/D-c 两次提交 | 记录：窗内容（脚本折叠/阶段时间线/并发可调）、「本会话始终允许」是否存在、Refine 是否可用、等待期间对话是否正常 |
| D-f1 | 技能门 428 | 新会话**不**加载手册直接要求起工作流 vs 通过 /ultracode 走完整前置 | 3.17.2 若有技能门：前者被拒、后者通过；若无技能门：两者皆通过——记录行为，校准手册 §2 第 1 条表述 |
| D-f2 | `files.read` 上限 | 大文件（>1MB）单代理读取脚本 | 记录拒绝或截断行为，回写设计文档 §1.2 |
| D-f3 | 命令技能挂载 | 插件方式安装后敲 `/ultracode` | 命令能自动挂载手册（`skills: ultracode` 解析）；若失败改用限定名 `ultracode:ultracode` 并回改 README |

## U' 系列：v2.0 验收

| # | 项 | 操作 | 判定标准 |
|---|---|---|---|
| U'1 | 并行 worktree 写入 | 同 D-c | 硬需求闭环：隔离写入、合并征询、冲突交用户、无孤儿残留 |
| U'2 | 评审-修复循环收敛 | `git commit` 一个含明显问题的改动，`/ultracode 按手册骨架 B 评审修复当前改动，最多 3 轮` | 循环 ≤3 轮收敛；评审失败的文件进「需人工介入」而非被当作通过；return 结构符合汇报契约 |
| U'3 | 中断后 resume | 起 D-a 的 run，中途关闭会话；新会话 `/ultracode 恢复刚才的扫描` | 模型走 ListWorkflowRuns → GetWorkflowRun → ResumeWorkflowRun；已完成的子代理不重跑（GetWorkflowRun 的 nodesCompleted 不回退） |
| U'4 | 汇报契约 | 观察 U'1-U'3 任一 run 的终态 | return 为小结构五字段；全文经 report/artifact；终态通知含 count+preview 而非全文；主代理按「结论→证据→确认情况→未覆盖」汇报 |
| U'5 | 闸门关闭报错 | 设置中关闭动态工作流（若可），`/ultracode 任意任务` | 明确报错「需在设置中启用」，不降级到 Agent 路径、不重试；测完恢复设置 |
| U'6 | 跨轮组合 | `/ultracode 先扫描概括，再对概括中风险最高的 2 个文件深挖`（两个 run） | 主代理按第一 run 的 return 发起第二 run；每轮有阶段汇报 |

## 顺序与通过标准

D-a → D-f（半天内可完成）→ U' 系列。**U'1（硬需求）与 U'5（单通道原则）为一票否决项**；其余 FAIL 项修复后重测。全部通过后：插件正式发版（push + marketplace 更新 + 版本记录），并将结果回写设计文档 §7 与 README 验收状态。
